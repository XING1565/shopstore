# 阶段 1 发布与回滚说明

> 所属：阶段 1 最小业务闭环（父 issue CESH-33 / ISSUE-0111）
> Owner：rebuild-ops
> 协作：rebuild-config（环境/配置）、rebuild-qa（验收依据）
> 状态：阶段 1 发布 / 回滚 / 备份恢复的运行手册；**ops 只负责到 staging，生产由人类 promote**

本文档说明阶段 1 交付物如何发布到 staging、如何验证、如何回滚与备份恢复，以及发布边界。
它是阶段 1 关闭的前置条件之一（父 issue「阶段 1 完成标准」中「发布 / 回滚 / 备份恢复说明完整」）。

## 1. 发布边界（先读这一节）

阶段 1 的发布由 agent（ops）执行**到 staging 为止**；生产部署始终由人类执行。

| 环境阶梯 | 名称 | 用途 | 操作人 |
| --- | --- | --- | --- |
| E1 | local | 本地开发 / 一键验收 | 全体 agent |
| E2 | test / acceptance | 干净环境端到端验收（ISSUE-0110） | qa / config / ops |
| E3 | **staging** | 预发布：镜像与配置经此验证后冻结 | **ops（agent 终点）** |
| E4 | production | 生产，对外营业 | **人类 only** |

硬性边界：

- **agent 永不部署生产（E4）。** ops 的职责到 E3（staging）为止，生产由人类 promote。
- **构建一次，promote digest，不重建。** 同一个镜像 digest 从 E2/E3 一路 promote 到
  E4，进入下一个环境时**不得重新 `docker build`**（重新构建会产生新 digest，破坏
  “已验证过的就是上线的那个”这一前提）。
- **不跳过 staging。** 任何变更必须先过 E3（staging）验证，才允许被人类 promote 到
  E4；没有 staging 验证记录的变更不得进入生产。
- 迁移是**显式、有门槛的**部署步骤（见第 4 节），不打包进 `start` / `up` 的隐式流程。

### 2.4 如何验证

发布到 staging 后，按以下顺序验证（复用阶段 0 冒烟 + 阶段 1 端到端验收）：

1. **服务健康**：`.\infra\scripts\shopstore.ps1 status`（Windows）或
   `bash infra/scripts/shopstore.sh status`，确认 Woo / Core / Odoo 均 PASS。
2. **Core 迁移到 head**：`alembic -c migrations/alembic.ini current` 显示 `0004`（head）。
3. **ops 级冒烟**：`.\infra\scripts\shopstore.ps1 test-smoke`（HTTP + Integration Mock 链路）。
4. **端到端主链路**（父 issue「阶段 1 最终验收流程」）：
   注册 pending 买家 → 未认证看不到批发价/MOQ → 运营审核 approved → 认证买家看到批发价与
   MOQ → 按 MOQ 无支付下单 → Core `Submitted` → Odoo 销售单创建（`odoo_sale_order_id` 写回）
   → 确认销售单 → 生成交货单 → 发货 → 状态回传 → Core `Shipped` → Woo 前台展示。
5. **负向与健壮性**：低于 MOQ 下单被拒并提示原因；同一订单不重复建销售单（幂等）；
   模拟一次同步失败，确认 `sync_jobs` 后台可见并可人工重试。
6. **备份—重启—数据仍在**：`backup` → `restart` → `test-smoke` → 数据仍存在。

staging 上 `seed` 仅在验收环境需要时执行；**生产/staging 业务数据禁用 seed**（见
`infra/STAGING.md`）。

## 3. 构建与镜像 promote（build once / promote digest）

阶段 1 的自研镜像只有 Core（`infra/docker/core.Dockerfile`）与 Integration 测试镜像
（`infra/docker/integration.Dockerfile`）；Woo / Odoo 直接使用官方维护镜像
（`wordpress`、`odoo:19.0`、`postgres:16`），tag + digest 锁定，无 `latest`。

发布流程（ops 执行，止于 staging）：

```text
1. 在干净 E2/验收环境跑通端到端验收（ISSUE-0110）
2. 构建一次镜像并记录 digest：
     docker build -f infra/docker/core.Dockerfile -t <registry>/shopstore-core:<tag> .
     docker inspect <registry>/shopstore-core:<tag> --format '{{.Id}}'   # 记下 digest
3. 把同一 digest push 到 registry（不做第二次构建）：
     docker push <registry>/shopstore-core:<tag>
4. 在 E3/staging 用该 digest 拉起，执行第 2.4 节验证
5. 验证通过后，staging 留发布记录（见第 7 节），交付给人类 promote 到 E4
```

关键约束：

- **同一个 digest 贯穿 E2 → E3 → E4**，中间任何一步都不得 `docker build`。
- 若 E3 验证失败，修复后**重新走完整流程**，生成新 digest，旧的废弃；不得“跳过 staging
  直接上生产”或“改一行直接在生产重建”。
- ops 只负责到第 5 步的 staging 记录；E4 的 promote 动作与时机由人类决定。

## 4. 回滚方式

按“最小范围优先”分级回滚。任一回滚前先执行第 5 节的 `backup`。

### 4.1 应用代码回滚（无数据库结构变更）

若问题只涉及代码且不涉及不可逆迁移：

```bash
# 回滚到上一个已验证的 git commit / tag
git fetch origin
# 在部署主机 checkout 到上一版本（例：v1.0.0 -> v1.0.0-rollback）
git checkout <上一已验证 tag/commit>
# 重新拉起（对 Core 会触发镜像重建 —— 仅在回滚场景允许；promote 场景禁止重建）
bash infra/scripts/shopstore.sh start
```

### 4.2 Core 迁移回滚

若问题由 Core 数据库迁移引入，且迁移可逆：

```bash
docker compose -f infra/docker/compose.yaml --env-file apps/core/.env \
  run --rm core alembic -c migrations/alembic.ini downgrade <上一版本>
```

- 仅回滚**可逆**迁移；包含破坏性/不可逆数据变更的迁移（如删列、删表）不得用
  `downgrade`，必须用第 4.3 节的备份整体恢复。
- 回滚后再把应用代码回退到与目标 schema 匹配的版本（4.1）。

### 4.3 数据整体回滚（兜底）

用最近一次备份整体覆盖恢复（见 `infra/RESTORE.md`）：

```powershell
# Windows
$env:CONFIRM = 'yes'
.\infra\scripts\shopstore.ps1 restore -BackupDir .\backups\<时间戳>
```

```bash
# Linux / macOS / Git Bash
CONFIRM=yes bash infra/scripts/shopstore.sh restore --backup-dir backups/<时间戳>
```

安全护栏：必须显式 `CONFIRM=yes`；仅允许 `APP_ENV=local/staging`（拒绝向 prod 类环境恢复）；
恢复是覆盖式的。

### 4.4 回滚后的验证

任一回滚后必须重跑：`status` → `test-smoke` → （涉及订单时）端到端主链路第 4~5 步。

## 5. 备份与恢复

阶段 0 已由 ops（ISSUE-0010）交付一键 `backup` / `restore`，阶段 1 直接沿用，无变更。

- **备份**：`.\infra\scripts\shopstore.ps1 backup`（或 `shopstore.sh backup`），输出到
  `backups/<时间戳>/`：
  `woo-mysql.sql`、`woo-uploads.tar.gz`、`odoo-postgres.pgdump`、
  `odoo-filestore.tar.gz`、`core-postgres.pgdump`、`manifest.txt`（含 git commit）。
- **恢复**：见 4.3 与 `infra/RESTORE.md`；Core 恢复后若 dump 版本落后于代码，补一次
  `alembic upgrade head`。
- **不在备份范围**（可由镜像/编排重建，非业务状态）：WordPress/Odoo/Core 的核心与插件、
  应用镜像本身。
- **演练（验收依据）**：`init → seed → backup → 破坏性改动 → restore → test-smoke/odoo
  verify`，数据回到备份时刻状态。

**备份目录与真实 `.env` 均在 `.gitignore` 忽略，绝不提交进 Git。**（见第 8 节）

## 6. 阶段 0 冻结版本约束

阶段 1 **不升级阶段 0 冻结版本**（`docs/版本清单.md`），沿用既有镜像 tag + digest。若
阶段 1 确需新增/升级某个组件版本，必须：

1. 新建 issue 记录：变更内容、理由、staging 验证结果、回滚方式（`docs/版本清单.md` §9/§10）。
2. 在 staging 按新版本组合启动 → 冒烟 → 数据迁移演练 → 通过后冻结进版本清单与 lockfile。
3. 同步更新 `docs/版本清单.md`。

未经 staging 验证的版本不得进入开发主线或生产。阶段 1 预期**无**此类变更；当前实际
使用的镜像（`odoo:19.0@sha256:d5a78a8c…`、`postgres:16@sha256:f1c3376c…` 等）与阶段 0
一致，无需更新清单。

## 8. 安全与验收清单

发布前逐项确认：

- [ ] 真实密钥 / 密码 / 凭据只存在于各主机 `.env`，仓库内只有 `*.env.example` 占位模板。
- [ ] 无本地数据库文件（`*.db` / `*.sql` / `*.dump` / `backups/` / `uploads/` /
      `filestore/`）进入 Git（均已被 `.gitignore` 覆盖）。
- [ ] `backups/` 目录仅在部署主机本地存在，未提交。
- [ ] staging 边界明确：ops 只发布到 E3，生产（E4）由人类 promote；构建一次、promote
      digest、不跳过 staging。
- [ ] 阶段 0 冻结版本未被升级；若需升级已记录理由 + staging 验证 + 回滚并同步版本清单。
- [ ] 迁移是显式、有门槛的步骤，未混入 `start` / `up` 隐式流程。
