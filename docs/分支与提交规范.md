# 分支与提交规范

## 分支策略

- 主干分支：`main`。仓库始终保持可运行、可验收状态。
- 一个 issue 对应一条工作分支，命名：
  - Agent 运行分支由平台自动创建：`agent/<agent>/<run>`（如 `agent/config/xxx`）。
  - 需要手动/约定命名时：`feat/<issue>-<slug>`、`fix/<issue>-<slug>`、`docs/<issue>-<slug>`、`chore/<issue>-<slug>`。
  - `<slug>` 小写 kebab-case。
- 禁止直接向 `main` 推送；通过 PR/MR 合并，并由对应 Agent 在 issue 中声明修改范围。
- 跨目录、跨模块修改必须在所属 issue 中说明，避免多 Agent 无边界改动同一模块。

## 提交信息格式

使用 Conventional Commits：

```text
<type>(<scope>): <subject>
```

- `type`：`feat`、`fix`、`docs`、`chore`、`refactor`、`test`、`build`、`ci`、`perf`。
- `scope`（可选）：改动所在的模块边界，如 `core`、`woo`、`odoo`、`integration`、`infra`、`docs`。
- `subject` 用英文小写开头，简洁陈述；正文可补充细节与关联 issue 编号（如 `ISSUE-0001`）。

示例：

```text
docs(infra): add env templates and directory skeleton for stage 0
feat(core): add health check endpoint
fix(woo): correct bridge callback url handling
```

## 提交纪律

- 不提交密钥、密码、token、`.env`、本地数据库与数据文件（见根 `.gitignore`）。
- 逻辑上相互独立的小步提交，避免把无关改动混入同一 commit。
- 提交前自查：`git status`、`git diff`，只暂存本 issue 范围内文件。
- 合并前确保本模块测试/验收通过；跨系统行为变更需说明影响面。
