## 0. 锁定原则

本清单遵循父 issue 的版本选择约束：

1. 优先选择当前仍维护、生态兼容的稳定版本。
2. 所有版本固定，禁止使用未锁定的 `latest`（Docker 侧锁定到具体 tag 或 image digest）。
3. WooCommerce / WordPress / PHP 三者必须相互兼容（按官方兼容矩阵选择）。
4. Odoo 与自定义模块（`marketplace_connector`）版本必须一致。
5. 后续升级必须经过 staging 验证后才允许进入开发主线。

## 2. 前台电商基座：WordPress + WooCommerce

### 2.1 版本选择

| 组件 | 版本 | 选择理由 |
| --- | --- | --- |
| PHP | 8.3.x | WooCommerce 10.8+ 要求 PHP 8.3+（官方测试至 8.4）；8.3 为当前维护中的成熟稳定版，生态兼容性最佳 |
| WordPress | 6.9.x | WooCommerce 10.8+ 要求 WordPress 6.9+；6.9 为当前稳定线 |
| WooCommerce | 10.8.x | 当前稳定大版本线（官方文档标注 "10.8 and later"），与 WP 6.9 / PHP 8.3 构成官方推荐兼容组合 |
| MySQL | 8.0.x | WordPress 官方要求 MySQL 8.0+ 或 MariaDB 10.11+，WooCommerce 要求 MySQL 8.0+ 或 MariaDB 10.6+；取 MySQL 8.0 为最通用且生态最成熟的交集 |

### 2.2 兼容性依据（已核对官方文档）

- WordPress 官方要求：PHP 8.3+，MySQL 8.0+ / MariaDB 10.11+。
- WooCommerce 10.8+ 官方要求：WordPress 6.9+，PHP 8.3+（测试至 8.4），MySQL 8.0+ / MariaDB 10.6+。
- 上述组合完全落在官方推荐区间内，无越界风险。

### 2.3 数据库备选

- MariaDB 10.11 LTS 可作为 MySQL 8.0 的等价替代（具备明确的 LTS 维护窗口）；二选一，不混用。默认取 MySQL 8.0.x，由 rebuild-config 在 ISSUE-0003 落地时确认最终选择。

## 3. ERP 基座：Odoo

### 3.1 版本选择

| 组件 | 版本 | 选择理由 |
| --- | --- | --- |
| Odoo | 19.0.x | 当前 LTS 大版本（LTS 节奏为 8/10/13/16/19），维护窗口最长，最符合"可稳定升级"目标 |
| Python（Odoo） | 3.12.x | Odoo 要求 Python 3.10+（v17 起）；3.12 为成熟稳定版，社区验证充分 |
| PostgreSQL | 16.x | Odoo 19 要求 PostgreSQL 13+；16 为成熟稳定版，且 ≥15 满足未来启用 AI 特性所需的 pg-vector 扩展 |

### 3.2 兼容性依据（已核对官方文档）

- Odoo 19.0 官方要求：Python 3.10+，PostgreSQL 13.0+（v19 起最低版本从 12 上调到 13）。
- 选择 PostgreSQL 16 而非最低 13，是为未来 pg-vector（需 15+）和更长的安全维护窗口留余量。

### 3.3 自定义模块约束

- `apps/odoo/addons/marketplace_connector/` 的 `__manifest__.py` 中 `version` 与所依赖的 Odoo 大版本必须一致，禁止混装跨版本模块。
- 阶段 0 只需 Sales / Inventory / Delivery 基础配置，不引入第三方 Odoo 模块；connector 为自研轻量 addon。

## 4. Marketplace Core 技术栈

### 4.1 选择结论

| 层次 | 选择 | 理由 |
| --- | --- | --- |
| 运行时 | Python 3.12 | 与 Odoo / Integration 同语言，团队只需维护 PHP + Python 两种运行时，CI / 运维面最小 |
| Web 框架 | FastAPI 0.115.x | 轻量、异步、原生生成 OpenAPI，直接支撑 ISSUE-0007 的 OpenAPI 契约产出 |
| ORM | SQLAlchemy 2.0.x | 成熟 ORM，与 Alembic 配套，满足 ISSUE-0005 的迁移机制要求 |
| 迁移 | Alembic 1.x | 标准迁移工具 |
| 数据校验 | Pydantic 2.x | 请求/响应校验，直接产出 JSON Schema |
| 数据库 | PostgreSQL 16.x | 与 Odoo 共用同一数据库引擎，运维只维护 MySQL（Woo）+ PostgreSQL（Core/Odoo）两类 |

### 4.2 能力阶梯评估（为何这样选）

按"原生配置 → 自研 hook → 三方插件 → 自研轻量插件"阶梯评估：

- Core 是纯自研服务，不涉及修改 Woo/Odoo 核心，无需走插件阶梯；框架选择以"最低复杂度满足 API + 迁移 + 契约"为准。
- 备选 Node.js/TypeScript 被否决：会引入第三套运行时（PHP + Node + Python），且 Odoo 适配器（XML-RPC/JSON-RPC）在 Python 生态更成熟，不必要增加复杂度。
- 备选 Django/DRF 被否决：功能全面但对本阶段"空模块 + 健康检查 + 契约"偏重，FastAPI 更轻、OpenAPI 原生。

## 5. Integration Layer 技术栈

### 5.1 选择结论

| 层次 | 选择 | 理由 |
| --- | --- | --- |
| 运行时 | Python 3.12 | 与 Core 同语言；阶段一可与 Core 同进程（保留清晰模块边界），后续再拆 |
| 统一 HTTP 客户端 | httpx 0.27.x | 同步 + 异步双接口，超时/重试可控 |
| 队列 | 阶段一用数据库任务表，不引入 Redis | 见 5.2 |

### 5.2 队列 / Redis 决策

- 阶段 0 / 阶段 1：使用数据库任务表（`sync_jobs`）承载同步任务、幂等键、重试与死信，避免提前引入消息中间件的运维成本。这符合架构方案"阶段一先跑通，后续再升级 Redis / Celery / Temporal"的原则。
- Redis：默认不启用。若后续阶段需要分布式锁 / 缓存 / 任务队列，锁定 Redis 7.4.x，并通过独立 issue 升级，升级必须经过 staging 验证。

### 5.3 适配器约束

- Woo Adapter、Odoo Adapter 均为自研轻量组件（不改 Woo / Odoo 核心）。
- Core 不直接依赖 Odoo API 细节；Integration 负责超时、重试、幂等、Webhook、死信与对账。

## 6. 前端 Node / npm（条件启用）

- 阶段 0 前台使用 WooCommerce 原生主题，不构建 Node 资产，因此默认不引入 Node。
- 若后续需要构建自定义块 / 前端资产，锁定 Node.js 22.x LTS + npm 10.x；启用时机由对应前端 issue 决定。

## 9. 版本冻结规则（落地约定）

1. 禁止 `latest`：Docker 用具体 tag / digest，语言依赖用 lockfile（`composer.lock`、`requirements.txt` / `pyproject.toml` 锁定、`package-lock.json`）。
2. WordPress / WooCommerce / PHP 作为"兼容三元组"整体升级，不单独跳某个版本。
3. Odoo 升级时，`marketplace_connector` 必须同步做版本适配并一起回归。
4. 所有版本变更必须新建 issue 记录：变更内容、理由、staging 验证结果、回滚方式。

## 10. 升级策略

```text
1. 在 staging 环境按新版本组合启动
2. 执行 ISSUE-0009 冒烟测试（健康检查 / 持久化 / Mock 链路）
3. 执行数据迁移演练（数据库备份 → 升级 → 校验）
4. 验证通过后，将新版本冻结进版本清单与 lockfile
5. 再推进到开发主线
```

- 未经 staging 验证的版本，不得直接进入开发主线或生产。
- 每次升级只动一个组件（或 Woo 三元组、Odoo+connector 这类不可拆分的组合），便于定位回滚点。
