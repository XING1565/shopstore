# 架构方案

## 1. 项目定位

本项目目标是构建一个参考 Faire 的 B2B 批发 marketplace。

开发策略不是从零重写所有能力，而是：

```text
WooCommerce 作为前台电商基座
Odoo 作为 ERP 和履约基座
Marketplace Core 补齐 marketplace 业务规则
Integration Layer 负责系统连接和可靠同步
```

能复用 WooCommerce 和 Odoo 的能力就优先复用；它们不能稳定承载的 marketplace 规则，再通过自研 Core 和轻量插件补齐。

Core 只保存 marketplace 运行所必需的数据，不复制 Odoo 的全部 ERP 数据。

```text
Core 保存：
  - Marketplace 买家、品牌和商品业务信息
  - 商品可见性、批发价和 MOQ
  - Marketplace 订单及外部系统 ID 映射
  - 跨系统编排所需的状态和审计信息

Core 不保存：
  - Odoo 全量库存流水
  - Odoo 全量仓库和库位数据
  - Odoo 全量采购、财务和会计凭证
  - Odoo 内部所有操作记录
```

## 3. 角色和模块关系

| 角色 | 主要入口 | 核心模块 |
| --- | --- | --- |
| 客户 / Retailer | Woo 前台 | 注册、认证状态、品牌发现、商品浏览、批发价、MOQ、采购单、订单状态 |
| Vendor / Brand | 阶段一由运营代维护，后续 Vendor Portal | 品牌资料、商品目录、供货信息、订单协作 |
| 运营 | Core Admin | 买家审核、品牌管理、商品管理、价格、MOQ、订单、同步异常 |
| 履约 | Odoo Inventory / Delivery | 库存检查、库存预留、拣货、打包、发货、物流信息 |
| 采购 | Odoo Purchase | 补货建议、采购单、供应商、入库 |
| 财务 | Odoo Accounting / Invoice | 发票、应收账款、对账、贷项 / 红字 |
| 管理员 | Platform Admin | 用户权限、系统配置、集成配置、日志、审计、备份、发布 |

## 4. 系统职责边界

### 4.1 WooCommerce / WordPress

负责前台体验和已有电商能力：

- 页面展示
- 内容管理
- SEO
- 商品浏览
- 购物车 / 采购单
- 无支付 checkout
- 买家账户入口
- 前台订单查询
- 轻量 B2B UI 插件

WooCommerce 不作为以下数据的最终真相源：

- 批发价
- MOQ
- 买家认证
- Marketplace 订单主权
- 库存
- 履约
- 财务

### 4.2 Marketplace Core

负责 Woo 和 Odoo 都不适合承载的 marketplace 业务规则：

- Retailer 买家档案
- 买家认证状态
- Brand 品牌档案
- 品牌和商品业务规则
- 商品可见性
- 批发价
- MOQ
- Marketplace 订单
- 订单状态机
- Woo / Odoo ID 映射
- 同步失败记录
- 人工重试

### 4.3 Odoo

负责 ERP 闭环：

- 客户
- 产品 SKU
- 销售单
- 库存
- 仓库
- 交货单
- 发货
- 采购
- 发票
- 应收账款
- 退货执行

阶段一先跑通销售单、基础库存、交货单和发货。后续再逐步加深采购、发票、财务和退货。

### 4.4 Integration Layer

负责连接和可靠性：

- 接收 Core 的领域命令和领域事件
- 将命令转换为 Woo / Odoo API 调用
- 接收 Woo / Odoo 的 Webhook 或同步结果
- 将外部系统状态转换为 Core 可理解的事件
- 将 Core 的业务状态投影到 Woo
- 幂等
- 重试
- 错误日志
- 对账

Integration 不决定价格、MOQ、订单是否成立等业务规则，也不直接修改 Core 的业务状态。
Core 只表达“业务上应该发生什么”，Integration 负责“如何可靠地传过去”。

Integration Layer 只负责“怎么可靠地传输”，不负责决定“业务上应该发生什么”。

```text
Core
  -> 产生领域命令 / 领域事件
  -> 例如：创建订单、发布商品、更新价格

Integration Layer
  -> 将命令 / 事件转换为目标系统 API 调用
  -> 负责超时、重试、幂等、Webhook、死信和对账

Core 不直接依赖 WooCommerce 或 Odoo API 的具体实现。
```

## 5. Product 商品主权和创建流程

### 5.1 Product 的三种投影

Product 不是 Woo、Core、Odoo 中三个互相独立的商品，而是：

```text
Core Product
  ├──> Woo Product
  └──> Odoo Product / SKU
```

三者关系：

| 对象 | 所在系统 | 作用 |
| --- | --- | --- |
| Core Product | Marketplace Core | Marketplace 商品业务主实体 |
| Woo Product | WooCommerce | 前台展示、采购单和购物车投影 |
| Odoo Product / SKU | Odoo | ERP 销售、库存、仓库和履约投影 |

### 5.2 阶段一商品创建流程

阶段一不做完整 Vendor Portal，商品由运营 / Admin 创建：

```text
运营 / Admin
  -> 在 Core 创建或维护 Marketplace Product
  -> Core 校验品牌、SKU、价格、MOQ 和发布规则
  -> Core 产生 ProductPublished / ProductUpdated 事件
  -> Integration 调用 Woo Adapter 创建或更新 Woo Product
  -> Integration 调用 Odoo Adapter 创建或更新 Odoo Product / SKU
  -> Core 保存 Woo Product ID 和 Odoo Product ID
```

### 5.3 商品数据写入规则

- 商品业务数据首先写入 Core
- Woo 只保存适合展示和购物车使用的商品投影
- Odoo 只保存 ERP 销售和履约所需的产品 / SKU 数据
- 库存数量、仓库、采购和财务字段不复制到 Core
- SKU 是 Core、Woo、Odoo 之间的稳定业务关联键
- Product 发布必须以 Woo 和 Odoo 投影创建成功为前提，或进入明确的同步异常状态

### 5.4 后续 Vendor Portal

后续开放 Vendor Portal 后，Vendor 仍然不能直接创建 Woo Product 或 Odoo Product：

```text
Vendor Portal
  -> 提交商品草稿
  -> Core 审核并创建 Core Product
  -> Integration 创建 Woo Product
  -> Integration 创建 Odoo Product / SKU
```

Vendor 的提交是业务申请，Core 才是商品业务主权。

## 6. Order 订单主权和外部 ID

### 6.1 订单对象关系

```text
Core
  -> 创建 Marketplace Order
       ├── marketplace_order_id
       ├── woo_order_id
       ├── odoo_sale_order_id
       └── odoo_delivery_id
```

三类订单不是三份独立业务订单，而是同一个 Marketplace 订单在不同系统中的投影和执行记录。

### 6.2 订单职责

| 对象 | 所在系统 | 作用 |
| --- | --- | --- |
| Marketplace Order | Core | 业务主订单、规则校验和生命周期 |
| Woo Order | WooCommerce | 前台结账和购物记录 |
| Odoo Sale Order | Odoo | ERP 销售执行 |
| Odoo Delivery | Odoo | 仓库出库和发货执行 |

Core 负责创建 Marketplace Order，Integration 负责创建 Woo / Odoo 的系统记录并维护 ID 映射。

## 7. 数据主权

Core 只保存 marketplace 需要的数据，不复制 Odoo 全部数据。

| 数据 / 对象 | 主系统 | 说明 |
| --- | --- | --- |
| Retailer | Core | Marketplace 买家档案和认证状态 |
| Brand | Core | Marketplace 品牌档案 |
| Core Product | Core | 商品业务主实体 |
| Woo Product | Woo | Core Product 的前台展示投影 |
| Odoo Product / SKU | Odoo | Core Product 的 ERP 产品投影 |
| 商品可见性 | Core | 买家能否看到商品 |
| 批发价 | Core | Marketplace 定价规则 |
| MOQ | Core | Marketplace 起订量规则 |
| 采购单 | Woo | 前台购物和结账过程 |
| Marketplace Order | Core | 业务主订单 |
| Woo Order | Woo | 前台结账记录 |
| Odoo Sale Order | Odoo | ERP 销售执行记录 |
| Odoo Delivery | Odoo | 仓库出库和发货记录 |
| 外部系统 ID 映射 | Core | 保存 Woo / Odoo 关联 ID |
| 库存 | Odoo | 不复制库存流水到 Core |
| 仓库 / 库位 | Odoo | 不复制 Odoo 仓储全量数据到 Core |
| 采购 | Odoo | 采购单、供应商和入库 |
| 发票 / 财务 | Odoo | 发票、应收和会计凭证 |
| 退货执行 | Odoo | 退货入库和库存处理 |
| 前台订单状态 | Core -> Woo | 面向买家的订单状态投影 |

## 8. 核心订单链路

```text
买家在 Woo 加入采购单
  -> Woo 发起无支付结账
  -> Core 校验买家认证、商品可见性、批发价和 MOQ
  -> Core 创建 Marketplace 订单
  -> Core 发布订单创建命令
  -> Integration 创建 Odoo 同步任务
  -> Odoo 创建客户 / 匹配客户
  -> Odoo 匹配 SKU
  -> Odoo 创建销售单
  -> Odoo 确认销售单
  -> Odoo 检查并预留库存
  -> Odoo 创建交货单
  -> 仓库人员在 Odoo 完成发货
  -> Odoo 状态回传 Core
  -> Core 更新 Marketplace 订单状态
  -> Woo 前台展示最新订单状态
```

## 10. Agent 协作模式

采用 issue 派发开发。

每个 issue 必须包含：

- 背景
- 目标
- 负责 agent
- 依赖 issue
- 修改范围
- 输入
- 输出
- 验收标准
- 风险点

推荐 agent 分工：

| Agent | 职责 |
| --- | --- |
| rebuild-pm | 需求拆解、排期、issue 派发、验收协调 |
| rebuild-architect | 架构、数据主权、状态机、API 契约 |
| rebuild-config | Woo / Odoo / 数据库 / 环境配置 |
| rebuild-dev | Core、Woo 插件、Odoo 模块、集成层开发 |
| rebuild-qa | 测试、验收、端到端流程验证 |
| rebuild-ops | 启动脚本、部署、备份、发布、日志 |

## 11. 技术边界建议

阶段一优先保证系统可跑通，不追求技术栈复杂化。

建议：

- WooCommerce 使用轻量自定义插件连接 Core
- Odoo 使用最小自定义 connector 或外部 API 调用
- Core 独立服务和独立数据库
- Integration 可以阶段一和 Core 放在一起，后续再拆
- 队列阶段一可以用数据库任务表，后续升级 Redis / Celery / Temporal

## 12. 架构底线

- 不直接共享 Woo 和 Odoo 数据库
- 不让 Woo 插件拥有订单主权
- 不让 Odoo 直接拥有 marketplace 规则
- 不做随意双向同步
- 所有外部系统 ID 必须在 Core 记录映射
- 所有跨系统调用必须可重试、可追踪、可人工修复
